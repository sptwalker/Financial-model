## 总体思路

- **验证优先**：计算引擎最先做，产出必须与 Excel 基线（`现金流测算 2026.8.xls` 中性情景）逐月对账一致，再谈界面与预测——数字错了，界面再漂亮也没用。
- **Ponytail**：费用全录入、收入为固定推导链 → 引擎用固定 Python 计算函数，不上通用公式引擎；预测先用 statsmodels，不上 Prophet。
- **复用**：飞书登录/JWT/RBAC/审计/Excel 导入全部移植自 `feishu_project_manager`，不重写。
- **数据先行**：开发第一天就要财务提供 3 份数据（见阶段 0），这是唯一的关键路径风险。

## 阶段 1 · 后端核心（8/24 – 9/14，约 3 周）⭐最关键

| 周 | 任务 | 交付物 / 验收标准 |
|---|---|---|
| 1 | 工程脚手架：FastAPI + SQLAlchemy 2.0 + Alembic + Pydantic v2；从 FPM 移植 Feishu OAuth/JWT/RBAC/审计/导入服务 | 可启动的 API 骨架；飞书登录闭环 |
| 1 | 数据模型落库：model/scenario/model_version/period/parameter/line_item/cell_value/assumption_schedule/import_batch 等表 + 迁移 | `alembic upgrade head` 通过 |
| 2 | **计算引擎**：收入推导链（线上/线下销售→配件→订阅）+ 三套回款账期（线上[0.5,0.5]、线下[0,1]、订阅[1]）+ 采购 N+2（可切 N+3）+ 现金滚转 + 年度汇总 | 引擎输出与 Excel 中性情景**逐月对账一致**（现金 5 行 + 销售额 + 回款 + 采购付款 + 费用）|
| 2 | 引擎/模型 API：参数、销量、费用增删改（动态可调）＋即时重算 | 改任意输入，输出即时变化 |
| 3 | Excel/CSV 导入：模板生成（**含渠道列**）、校验、导入批次；含税口径直算 | 导入 D1–D4 数据，入库可查 |

**阶段 1 退出标准**：用真实数据重建出与 Excel 一致的"中性"基准情景。

## 主要风险与对策

| 风险 | 对策 |
|---|---|
| 财务数据（D1–D4）拖延 → 全计划顺延 | 阶段 0 立即启动，开发前两周只依赖 D1 起数 |
| 引擎与 Excel 对账不一致 | 阶段 1 专设对账周（W2），逐行 diff 定位口径差异 |
| 历史销量仅 28 个月、季节周期少 → 预测不可靠 | 如实呈现置信区间，回测选优，不硬推高阶方法 |
| 飞书应用配置（回调域名/权限）需公司 IT 配合 | 阶段 1 第一周即提交飞书自建应用申请 |
| **真实个人隐私数据（工资表/社保/公积金）留在仓库中** | 阶段性合规风险：移出仓库、改为脱敏夹具；详见验收报告 §6 |
