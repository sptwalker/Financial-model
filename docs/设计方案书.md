# 创想悦动 · 现金流测算与预测系统 设计方案书

> 版本：v0.1（设计稿） · 日期：2026-08-20 · 状态：待评审

## 1. 项目背景与目标

将现有 Excel 现金流测算模型（`现金流测算 2026.8.xls`）升级为可部署、可协作、可预测、可视化的 Web 系统。

**核心目标**
- 把 Excel 的驱动型现金流模型变成**动态网页**：参数、销量、费用等所有收入/成本项**在线可增删改**，改动即时重算。
- 支持输入**历史销售数据 + 预测假设**，用**统计/机器学习**方法预测未来销量并推导各项财务数据。
- 面向高管的**动画化、直观、手机适配**的图表看板。
- **飞书登录 + 三级角色权限**，财务数据可审计。
- 预留**扩展适配层**，未来对接人事/生产/营销系统（前期均表格导入）。

## 2. 需求概述

**功能性**

|---|---|---|

| F2 | 计算引擎 | 收入拆分→回款→采购成本→费用→现金流→利润表，逐月 + 年度汇总 |
| F3 | 情景管理 | 中性/乐观/悲观 + 自定义，多情景并排对比 |
| F4 | 版本快照 | 模型版本留痕，可发布/归档，可复盘（预测 vs 实际） |
| F5 | 预测 | 由历史销量做统计/ML 预测，回测+置信区间，可回填为销量驱动 |
| F6 | 数据导入 | Excel/CSV 模板导入历史开票量、销量、费用等，逐行校验 |
| F7 | 可视化看板 | ECharts 动画图表，高管驾驶舱 |
| F8 | 导出 | 现金流表/利润表导出 Excel/CSV |

**非功能性**
- 飞书自建应用 OAuth 登录 + JWT；三级 RBAC；关键财务写操作审计（前后值留痕）。
- 手机屏幕适配（高管看板移动优先）。
- 中文优先界面；金额用 `Decimal`，单位统一（内部规范化，展示层换算 元/万元/万台）。
- 全站 HTTPS；敏感密钥仅后端持有。
- 可扩展：新增数据源/科目/情景不改核心 schema。

## 3. 对现有 Excel 模型的解构

该 Excel 是**驱动型逐月现金流模型**，四个工作表：

1. **现金流中性（主模型）**
   - 参数：线上价 1799 / 线下价 1475.18 / 采购价 1150（元）；配件销售占比 0.5、单台配件收入 200；订阅比例 0.7、单台订阅收益 200；线上营销费率 0.30、线下综合费率 0.23；年度销量目标（万台）2026H2=2.98 / 2027=14.6 / 2028=30 / 2029=75。
   - 时间轴：2026-07…2027-12 **逐月**，其后 2028、2029 为**年度列**（异构粒度）。
   - 现金流块：期初现金 / 本期支出 / 本期回款 / 本期现金缺口 / 期末现金（逐期链式结转）。
   - 销售块：硬件销量（线上/线下）→ 售价 → 配件收入与占比 → 平台增值占比 → 单台会员订阅收益 → 销售额合计（线上/线下/增值/订阅）→ 回款合计。
   - **回款滞后于销售额**（部分当月、部分次月的**混合账期**，非整月平移）。
   - 采购/COGS：采购付款合计 = 整机采购（1150×台）+ 配件采购，付款亦有账期。
   - 费用块（约 12 项）：工资、游戏外包开发、商业IP、版号、办公硬件、信息技术服务、房租、招聘费、办公及其他、品牌宣传、渠道佣金、渠道推广费、线上推广费，另有人数行。**部分直接录入、部分疑似公式驱动**（如渠道佣金≈销售额百分比、线上推广费≈线上营销费率×线上销售）。
2. **Sheet7**：中性/乐观/悲观**三情景**（改年度销量假设），各带 2027 利润表（收入/成本/费用/营业利润）。
3. **订阅收入**：会员订阅收入由**累计装机量**滚动驱动（2026–2029）。
4. **N**：历史开票/出货量 2023-08…2025-12（约 28 个月，累计约 113 万台）——预测的历史数据源。

> 结论：系统 v1 以本模型为**内置模板**，但科目/参数/情景**皆可配置**，计算引擎支持「直接录入 / 公式驱动」两种科目，并支持逐月+年度混合粒度。

## 6. 计算引擎设计（核心 #1）

**心智模型**：一个模型 = **科目行 × 期间列** 的网格。每行是 **INPUT**（按期存值）或 **FORMULA**（一条表达式逐期求值）。期间轴**异构**：18 个月列 + 2 个年度列；现金台账沿有序期间列表逐期结转，与粒度无关。

**输入 schema**
```
parameters[]  : { key, label, value:Decimal, unit, group, sort }
periods[]     : { seq, granularity:'month'|'year', year, month?, label }
line_items[]  : { key, label, category, kind:'input'|'formula',
                  formula?, agg:'sum'|'last'|'avg'|'mean', unit, sort, active }
cell_values[] : { line_item_key, period_seq, value:Decimal, source, is_override, note }
schedules[]   : { kind:'collection'|'payment', channel?, weights:[w0,w1,…], label }
                回款(t)=Σ_k w_k·销售额(t−k)   （按渠道混合账期）
                已确认(§15)：线上[0.5,0.5]、线下[0,1]、订阅/增值[1]（即时）；采购付款 N+2→[0,0,1]，可切 N+3→[0,0,0,1]
```
`category ∈ {sales, cogs, opex, cashflow, subscription, headcount}`。科目/参数**隶属于某个模型版本**，故增删改即行级 CRUD → 满足“动态可调”。

**公式表示与安全求值**
- 公式是**文本表达式**，引用其它科目 key、参数 key、及**白名单辅助函数**；**禁用 Python `eval`/import/属性访问**。
- 求值器：`simpleeval`（专用安全算术求值；零依赖备选：约 40 行 `ast` 白名单求值器）。
- 每期命名空间：`{参数→标量} ∪ {科目→本期值} ∪ 辅助函数`：
  - `lag(row,n)` 取 t−n 期值；`cumsum(row)` 截至本期累计（驱动 累计装机量→订阅）；`collect(row,'collection')`/`pay(row,'payment')` 账期卷积。
- 执行：解析引用 → 建 **DAG** → 拓扑排序 → **逐期从左到右**求值（`lag/cumsum` 读已算的前期）；成环即报错并定位到编辑器。
- 规模 ~25 行 × ~20 期 ≈ 500 单元格，逐单元格朴素求值即可（可读性优先）。

> 已确认(§15)：**费用行当前全部直接录入**（kind=input），MVP 不启用费用公式，预测期费用亦全部手动可调。公式/结构仅用于**收入推导链**：`线上销售=线上台数*线上价`、`线下销售=线下台数*线下价`、`整机采购=采购台数*采购价`、`订阅=cumsum(装机量)*订阅比例*单台订阅收益`。
> ponytail：既然无用户自定义公式，MVP 可将该链实现为**固定 Python 计算函数**，`simpleeval`/公式 DAG 推迟到真出现用户自定义公式再引入。

**输出 schema（逐期 + 年度汇总）**
```
销售   : 线上/线下台数, 线上/线下销售, 配件收入, 增值收入, 订阅收入, 销售额合计
回款   : 回款(按 collection 账期)
成本   : 采购台数, 整机采购(1150·台), 配件采购, 采购合计, 采购付款(按 payment 账期)
毛利   : 毛利额, 毛利率%
费用   : 各费用行, 费用合计, 人数
现金流 : 期初, 支出, 回款, 缺口, 期末   （期末=期初+回款−支出；下期期初=本期期末）
利润表 : 收入, 成本, 费用, 营业利润   （按情景，如 FY2027）
```
**逐月+年度并存**：引擎按原生期间计算；**汇总视图**把月列按财年聚合（流量科目 `sum`、期末现金/累计装机量 `last`、人数 `mean`），原生年度列（2028/2029）直通。高管看年度、财务看逐月，同一次计算得出。

**持久化**：仅存 INPUT 单元格，输出按需实时计算（毫秒级）并可缓存到版本上；已发布快照冻结其输出用于审计/复盘。

## 7. 预测模块设计（核心 #2）

**数据现实**：约 28 个月、强年度季节性、但仅约 2.3 个季节周期——足够 level+trend+粗季节性，但对稳健乘性季节性/高阶 SARIMA 偏紧张。设计上**如实呈现不确定性**（宽置信带、稳健方法优先、标注过拟合风险）。

**方法阶梯（取回测最优者）**
| 级 | 方法 | 依赖 | 何时用 |
|---|---|---|---|
| 0 | 季节朴素(去年同月)+移动平均 | 无 | 恒作基线/合理性下限 |
| 1 | **Holt-Winters / ETS**（statsmodels，m=12 加性） | statsmodels | **默认主力** |
| 2 | SARIMA（`SARIMAX`，可选 `pmdarima.auto_arima`） | +pmdarima(可选) | 回测胜过 ETS 时 |
| 3 | Prophet（节假日 双11/春节 回归） | 重（Stan） | **v2** |
| 4 | 梯度提升 lightgbm（滞后+日历+营销费特征） | 重 | **v2**（历史增长/外生变量到位后） |

> 预测核心依赖仅 **statsmodels**；2 级以上为可选 extras。

**回测与区间**
- **滚动起点（扩窗）CV**：训练→预测 h→前滚；28 点用短横 h=1..3、少折。按方法/折报 sMAPE/MAPE/MAE/RMSE。
- 自动选最优（最低 sMAPE），但**始终允许用户覆盖**选择。
- 置信区间：ETS/SARIMAX 原生预测区间；朴素法用残差经验区间。图上画带——稀疏数据下“宽带”本身即诚实。

**预测如何回填驱动（关键）**
```
历史(sales_actual) → 预测器 → 逐月总台数 + 置信区间
                                    │
              线上/线下拆分(可配：固定比例 | 历史学习 | 计划渠道迁移)
                                    │
                             forecast_result 行
                                    │
        预测工作台复核：原样接受 / 逐月编辑 / 缩放到目标
                                    │
             “接受”写入目标情景草稿版本的 cell_values(source='forecast')
                          = 硬件销量驱动序列
```
**自上而下 × 自下而上对账（亮点）**：管理层年度目标（2027=14.6万、2028=30万…）用**预测得到的季节形状**分摊到各月，硬指标也能得到贴近现实的月度曲线。接受动作绝不静默覆盖——落为可编辑、可审计的驱动修订。
> 已确认(§15)：**2028/2029 用季节曲线月度化**（即此处的季节分摊）；**线上/线下拆分**：模型表逐月销量已分渠道（线上/线下两行），以其实际占比为初始拆分比例；`N` 历史出货表仅总量、无渠道列——待导入分渠道历史后切换"按历史学习"。

## 8. 数据模型（PostgreSQL）

两条设计主线：(1) **高表 `cell_value`** 承载所有随期变动的数值，透视即 科目×期间；(2) **`model_version` 作为快照/审计/分支单元**，所有配置行外键到它，“新版本”= 深拷贝。

```
users(id, feishu_user_id*uniq, name, position, avatar_url, department,
      role[admin|editor|viewer], status[pending|active|disabled], last_login_at, ts)

model(id, name, note, created_by→users, ts)
scenario(id, model_id→model, name, type[neutral|optimistic|pessimistic|custom], sort)
model_version(id, scenario_id→scenario, label, status[draft|published|archived],
      parent_version_id→self, is_baseline, created_by, note, ts)          ← 快照单元

period(id, version_id→model_version, seq, granularity[month|year], year, month?, label)
parameter(id, version_id, key, label, value NUMERIC, unit, grp, sort)      ← 标量
line_item(id, version_id, key, label, category, kind[input|formula],
      formula TEXT?, agg, unit, sort, active)                              ← 行 schema
cell_value(id, version_id, line_item_id→line_item, period_id→period,
      value NUMERIC, source[input|formula|forecast|import], is_override, note)
      UNIQUE(version_id, line_item_id, period_id)                          ← 高表事实
assumption_schedule(id, version_id, kind[collection|payment], weights JSONB, label)

sales_actual(id, year, month, channel[online|offline|total], units, revenue?, source) ← 表N+未来
forecast_run(id, scenario_id, method, params JSONB, horizon, train_range, metrics JSONB,
      status, created_by, ts)
forecast_result(id, run_id→forecast_run, year, month, yhat, yhat_lower, yhat_upper,
      split_online, split_offline)

connector(id, type[excel|hr_api|mrp_api|marketing_api], name, config JSONB, enabled, last_sync_at)
import_batch(id, connector_id?, kind[history|volume|expense|actuals], filename,
      uploaded_by, row_count, error_count, status, ts)
staging_fact(id, batch_id?/connector_id?, metric_key, year, month?, dimension JSONB,
      value NUMERIC, ingested_at, promoted BOOL)                          ← 规范化落地
audit_log(id, actor_id, actor_name*snapshot, action, entity_type, entity_id,
      before JSONB, after JSONB, occurred_at)                            ← 前后值留痕
```
关系：`model 1─* scenario 1─* model_version 1─* {period, parameter, line_item, cell_value, schedule}`；`scenario 1─* forecast_run 1─* forecast_result`；`import_batch/connector 1─* staging_fact` → 提升 → `cell_value`/`parameter`/`sales_actual`。

> 为何用高表 `cell_value`：逐月与年度同构落地（期间携带粒度）；透视即 `GROUP BY 科目,期间`；增科目/增期间不改表结构。纯标量留在 `parameter`；年度销量目标是年度期间上的 `cell_value`。

| **驾驶舱**（高管） | 一屏看健康度 | 动画：现金余额跑道折线/面积、期末现金瀑布图、收入构成堆叠柱（线上/线下/增值/订阅）、情景 KPI 卡、FY 利润仪表/柱 |
| 模型编辑器（财务） | 编辑网格 | 可编辑 AntD Table（科目×期间）；录入格可改、公式格只读带 ƒ 徽标+悬浮公式；实时 preview 重算 |
| 假设与参数 | 参数+账期 | 参数表单、回款/付款权重编辑器 |
| 情景对比 | 三情景+自定义 | 并排列、差异热力、小多图折线 |
| 预测工作台 | 预测 | 历史折线+置信带预测、方法选择、回测指标表、线上/线下拆分滑杆、接受/缩放到目标 |
| 导入中心 | Excel/CSV | 模板下载、上传、校验预览（行→错误）、提交 |
| 管理 | 用户/连接器/飞书配置 | 待审批用户表、角色选择、连接器卡片 |
| 审计日志 | 改动留痕 | 可筛选表、前后值 diff 抽屉 |

**手机策略**：AntD 响应式 `Row/Col`（卡片自动堆叠）；高管驾驶舱**移动优先**（KPI 卡→图表，按优先级排布）；ECharts `ResizeObserver` + 响应式 `media`；宽编辑网格在手机降级为**只读卡片/表**（重编辑面向桌面，查看随处可用）；图表配表格降级以利可访问性。

## 11. 集成 / 适配层（核心 #3）

让“现在 Excel、未来 API”成为配置而非重写的契约：
```python
class Connector(Protocol):
    type: str
    def fetch(self, since: date | None) -> Iterable[StagingFact]: ...
    # StagingFact = { metric_key, year, month?, dimension:dict, value }
```
- 所有数据源实现同一个 `fetch()`，统一落到**一张 `staging_fact`**（metric_key + 期间 + 维度 + 值），无按源建表。
- **受控 `metric_key` 词表**（`shipment_qty, headcount, salary_cost, marketing_spend_online, unit_cost…`）= 外部世界与模型之间的稳定接口。
- **提升(promotion)** 按小型映射把 `staging_fact.metric_key → 目标`（某 `parameter.key` / 某 `line_item`+`period` 单元格 / `sales_actual`）；提升处需**编辑角色人工确认**方可触达模型。
- **MVP 仅发 `ExcelConnector`**（包住 FPM 的导入）。未来 `HrApiConnector`/`MrpConnector`/`MarketingConnector` = 实现 `fetch()` + 声明映射即可，**计算引擎、数据模型、UI 均不变**——这就是“无重写”属性。

## 12. 安全与权限

**飞书 OAuth 流程（移植 `core/feishu.py`）**
1. 前端 `POST /auth/feishu/login` → 后端 `get_oauth_url(state)`（CSRF state）。
2. 用户在飞书授权 → 回调 `GET /auth/feishu/callback?code&state`。
3. 后端 `app_access_token` → `user_access_token(code)` → `user_info`。
4. **upsert 用户**；新用户 `status=pending`（数据门禁前拦截），`INITIAL_ADMIN_FEISHU_IDS` 自动提升引导管理员。
5. 签发自有 **JWT access+refresh**（jose，`type` claim）；前端带 `Bearer`。

**角色矩阵**
| 能力 | 查看 | 编辑 | 管理员 |
|---|:--:|:--:|:--:|
| 看板/报表/导出 | ✅ | ✅ | ✅ |
| 改参数/驱动/费用、跑预测、导入、建情景与草稿版本 | ❌ | ✅ | ✅ |
| 发布/归档/删除版本 | ❌ | ⚠️ 仅发布 | ✅ |
| 管理用户与角色、连接器、飞书配置 | ❌ | ❌ | ✅ |

**审计**：每次财务写入（参数/单元格/费用编辑、预测接受、导入提交、版本发布、角色变更、连接器配置）→ `audit_log` 含 **before/after JSON**；仅追加、不可改。
**传输/密钥**：Nginx TLS；JWT `SECRET_KEY` 强度校验；CORS 白名单；飞书 app secret 仅在后端 env/DB 设置；Postgres 最小权限。

## 13. 部署方案

Docker Compose：`nginx`（TLS + 静态 SPA + /api 反代）+ `api`（uvicorn 多 worker）+ `postgres`（挂载卷）。Alembic 迁移在启动脚本执行。环境变量：飞书 App ID/Secret、`SECRET_KEY`、DB URL、`INITIAL_ADMIN_FEISHU_IDS`、允许的回调域名。可部署到贵司 Linux 服务器或阿里云/腾讯云；域名/ICP/证书由贵司提供。

## 15. 财务已确认的建模口径（2026-08-20 确认）

财务已确认下列规则，计算引擎据此实现（详见 §6 账期、§7 预测）。所有规则仍为系统内**可配置项**，后续可调。

| # | 口径 | 已确认规则 | 引擎落地 |
|---|---|---|---|
| 1 | 回款账期 | **线上**＝本月销售额×50%＋上月销售额×50%（当月约15天到账）；**线下**＝次月全额（N+1）；**订阅**＝当期即时到账 | collection 按渠道三套权重：线上 [0.5,0.5]、线下 [0,1]、订阅 [1] |
| 2 | 采购付款账期 | 当前 **N+2**，后续改 **N+3**，**须可配置**；整机与配件同口径 | payment 权重 [0,0,1]→[0,0,0,1]，单一可调 |
| 3 | 各费用行 | **全部直接录入**，不用公式；预测期费用亦全部手动可调 | 费用行 kind=input |
| 4 | 期初现金 | 取现金流量表的**期初现金**为种子 | 首期 cashflow 期初 |
| 5 | 税 | 现金流量表**已含税**，售价/采购价均**含税**；不单列增值税，暂不计企业所得税 | 含税口径直算，无税模块 |
| 6 | 订阅时点 | 订阅**按期回收、当期即时到账**；2026-07 前**装机量初值**取现金流量表数值 | 按累计装机量逐期确认，w0=1 |
| 7 | 2028/2029 粒度 | **用季节曲线月度化**（历史季节形状把年度目标摊到 12 月） | 年度目标→季节分摊→月度驱动 |
| 8 | 线上/线下拆分 | 模型表逐月销量已分渠道，**以其占比为初始拆分**；后续按导入的**带渠道列**历史学习 | 初始比例=模型自身线上/线下占比；N 表无渠道列 |
| 9 | 单位口径 | 内部强制统一、仅展示层换算 | Decimal 规范化＋展示换算 |

**仍需补齐的小项（已假设默认，不阻塞开发）**
- **配件回款**：默认随其销售渠道走（线上配件按线上账期、线下配件按线下账期）。✅ 财务已确认（2026-08-20）。
- **平台增值收入**：默认与订阅同为当期即时到账。✅ 财务已确认（2026-08-20）。
- **拆分学习的数据前提**：模型表逐月销量已分渠道（已核实，2026-07 起”硬件销量”下含线上/线下两行）→ 初始拆分比例直接用模型自身占比；现有 `N` 历史表仅总量（已核实），需后续导入**带渠道列**的历史，再切自动学习。
